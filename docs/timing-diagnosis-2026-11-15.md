## 候选原因与区分方法

| 候选原因 | 本次证据与代码边界 | 如何区分 |
| --- | --- | --- |
| 列表没有刷新 | 列表值与 Service 已用量一致，底层确实只有约 12 秒，不能仅归为显示问题 | 同时比对 `usedMs`、剩余量和页面读数 |
| 周期恰好重置、配置更改、时钟变化 | 当前起点不支持在 07:13–07:25 跨界；规则使用单调时钟，已有编辑保留本轮额度的回归 | 保存实际/待生效参数、周期边界、规则时间与两个系统时钟 |
| 包名不匹配、分身/不同用户、目标不可用 | 系统记录与配置均是同一红果包；采集时目标 eligible。没有本次错误用户/分身的证据 | 比对系统活动的用户、包与 eligible；记录包变动后重载原因 |
| 杀进程、撤权、服务断开 | 没有今天新增进程退出，当前绑定正常，不支持直接套用此前一键清理问题；短暂断连仍不能绝对排除 | 持久记录进程会话、连接/解绑/销毁/中断、系统退出原因，并对照系统绑定 |
| **横屏过程中产生未知系统窗口** | 优先排查。代码将不在白名单中的 SystemUI 事件视为离开，清空前台并取消 tick；如果面板退出后没有目标事件，会一直停止 | 重放目标→未知系统窗口→不再发目标事件；实机需对照真实窗口焦点与事件链 |
| 横竖屏本身、目标内部页面切换 | 同包目标事件仍识别为目标，不应仅因类名或 fullScreen 改变而停表；不能等同于伴随系统窗口的真实切换 | 重放同包竖屏→横屏→持续无事件，与上一行分开 |
| 桌面/最近任务尾随事件 | 现有保护依赖 PANE_APPEARED 和 1.5 秒返回窗口；缺失信号或更迟尾随事件仍可能清空 | 原最近任务生产 Service 回归，日志增加 PASS/DEFER/IGNORE 与事件时间 |
| 空包名、其他窗口事件 | 空包名和非目标事件都会清空目标；这是可模拟的停止路径，尚无本次现场证据 | 单独记录 no-package，其他 App 只记录 other，不保留其身份 |
| 锁屏、息屏/亮屏广播、onInterrupt | 均会清空前台；亮屏后新目标事件之前不恢复。07:10 已解锁，07:13 才进红果，现存 events 未显示使用区间内再次锁屏，故优先级较低 | 记录具体屏幕 action、中断原因、interactive/locked，以及清空后的事件水位 |
| 迟到事件或错误水位 | 早于水位的事件会被忽略；若真正恢复事件也早于水位，可能无法重新开始；未取得本次原始事件时间 | 同时记录接收 uptime、eventTime、age、watermark 与忽略判定 |
| 主线程卡顿、深度休眠、系统冻结 | 超过 2 秒或两个时钟不一致的样本被拒绝，避免把休眠补成使用；本服务实例 rejected=0 不支持持续采样被丢弃，但“采样已停”不会增加 rejected | 主线程停顿重放、已有双时钟边界测试，记录 tick 延迟、样本差值与 30 秒服务心跳 |
| 存储失败、重复计时水位或规则更新异常 | 约 5 秒落盘延迟本身不能解释内存中漏掉 11 分钟；失败提交会暂停建立有效观察区间 | 记录 commit 失败、saved、accountedUntil、周期/用量；日志文件写失败与规则保存失败分开 |
| 遮罩挂载失败 | 单独的遮罩错误不能解释累计量仍为 12 秒；需要先达到额度 | 记录挂载/移除/异常及原禁用截止，与累计量一起看 |
| 分屏、画中画、其他显示器 | 首版覆盖普通全屏，本次系统记录为横屏活动，没有分屏/画中画证据 | 下一次同时采集窗口/活动信息，不仅依赖 fullScreen 标志 |

`TYPE_WINDOW_STATE_CHANGED` 表示界面中视觉上独立区域的变化，并不保证“顶层活动 App 已切换”。依据：[Android AccessibilityEvent](https://developer.android.com/reference/android/view/accessibility/AccessibilityEvent#TYPE_WINDOW_STATE_CHANGED)。因此未知 SystemUI 事件的停止路径值得优先复现；不能为了绕过漏计而把所有 SystemUI 窗口一律视为透明，通知栏和锁屏仍需停止限制。

## 诊断设计

- 自动记录进程版本/会话、前三条系统进程退出原因、Activity 创建、服务连接/解绑/销毁/中断、屏幕广播、规则/包重载、前台切换与原因、事件水位/年龄/窗口 ID、目标与 SystemUI 类名、最近任务决策、拒绝样本、延迟 tick、存储失败和遮罩结果。
- 开始/停止、禁用变化以及每 30 秒保存状态快照，含所有配置目标的实际/待生效参数、已用/剩余、周期边界、已计时水位和规则时钟。即便前台为空，服务心跳仍能区分“活着但没有目标”和“进程/回调长时间没有运行”。普通 Handler 不主动唤醒休眠设备。
- 单个后台工作线程写入 `noBackupFilesDir/timing-diagnostics/`，4 × 256 KiB 轮转，按容量淘汰最旧记录。队列最多 256 项，满时丢诊断并报告数量；文件 I/O 失败仅记录失败计数/类型，不中断规则计时。不是保证保留几天的完整历史，极端突发事件和进程突然退出仍可能丢尾部排队记录。
- 不增加权限、不读节点/事件文本/窗口内容、不保存未配置 App 的包名/类名，不联网；文件不参与备份。完整 ADB 系统材料可能包含其他 App 信息，采集目录默认仅当前用户可读，应仅本机留存。
- `dumpsys activity service com.goule.prototype/.FreezeService --history` 输出当前状态和持久历史。服务已断开时，用户重新打开斩心魔，再用 `dumpsys activity com.goule.prototype/.MainActivity --history` 读取前一次进程日志；无需为了采集重新开关无障碍权限。

## 下次故障的采集方法

1. 记下大致发生时刻、目标 App、是否横屏/音量面板/通知栏/锁屏/最近任务，以及列表读数。先保留现场，不重装、清数据或重新开关服务。
2. 手机连接已授权 USB ADB 后执行：

   ```sh
   python3 scripts/collect_timing_diagnostics.py --serial <adb序列号>
   ```

   默认写入本机 `~/.cache/goule-android/timing-日期-时间/`。同时保存服务/Activity 历史、系统绑定、退出历史、包版本、焦点、进程、电源、系统日志及使用事件；不启动 App、不改权限、不清日志。
3. 需要现场重现时加 `--watch-seconds 180`，再由用户正常使用目标、切横屏约 20 秒后返回。脚本每秒保留服务状态与窗口信息，再保存结束日志。它不会修改戒律，真实使用仍按原配置消耗额度。
4. 服务已断开时，先做一次采集保存当前系统状态；然后用户打开斩心魔，再采集一次导出保留下来的应用日志。不要把“打开主界面”当作服务已经恢复。
5. 对齐 `wall/up/elapsed/session`，找最后一次有正常累计的目标记录，随后查看清空 reason、被忽略事件或样本拒绝；如没有事件而心跳还在，查前台为空的起点；如连心跳都中断，结合新进程的退出历史和系统绑定判断。

旧版 0.3.13 不会凭空获得持久历史；新增诊断必须安装包含本次改动的 APK 才能生效。
